# テスト戦略資料 — テスト観点一覧（Testcase Viewpoints）

## 1. 資料目的

本資料は **システム全体のテスト戦略**であり、個別テストケースのリストではない。
QAチームが各画面 ACSMS-SCR-XXX のテストケースを設計する際に確認すべき
「観点（视点）」を定義する。各観点は **業務またはテクニカルなリスク軸** を
表し、複数画面を横断して適用される。

### 本資料の必要性

ACSMS は約31画面で構成される。各画面が独立してテストケースを設計すると、
日本案件で典型的な以下3つの問題が発生する。

1. **カバレッジの不均衡** — 画面Aには入力バリデーションが80件、画面Bには
   20件など → 顧客レビュー時にギャップが発覚 → 期末に手戻り発生。
2. **記述の重複** — 同じ「SQLインジェクション入力」観点の表現が31通り存在し、
   監査が困難。
3. **システム横断リスクの見落とし** — 「同時編集テスト」「操作中のセッション
   失効テスト」など、全画面で統一して実施すべきだが個別テスター間で漏れ
   やすい観点。

観点資料は以下の方法でこれらを解決する：

- リスクを **6グループ × 44観点** に分割。
- 各観点に **リスクレベル**、**適用範囲**、**テストケース設計方法**、
  **典型的な落とし穴** を明記。
- 各画面の機能シートでは、自テストケースを `観点ID` にマッピングするだけで
  済み、レビュアーは1スキャンでカバレッジ充足を判定可能。

### 本資料の使い方

| 役割 | 行動 |
|---|---|
| テストリード | 観点をレビューし、リスクレベルを設定、顧客と承認 |
| QA設計者 | 新画面のテストケース作成時、各観点を確認し、適用観点ごとに1件以上のケースを用意 |
| QA実行者 | テスト実行時に各ケースの `観点ID` を記録し、どの観点をカバーしているか把握 |
| レビュアー／顧客 | 機能シートを読む**前**に本資料を読み、全体戦略を理解してから詳細に入る |

### リスクレベル

- **高** — データ消失、権限誤判定、情報漏洩、監査ログ破損を引き起こす
  バグ。リリース前に100%テスト。
- **中** — 数値誤り、UX破綻、業務遂行不能を引き起こすバグ。
  サンプリング 70-80% でテスト。
- **低** — UX、レイアウト、性能エッジケース。スポットチェックのみ。

## 3. 観点詳細

### グループ A — セキュリティ・権限

#### VP-A-01 — ロール別権限制御（RBAC gate）

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | `meta.permission` を持つ全画面（約25/31画面） |
| **TC見積** | 約265（5ロール × 25画面 × 平均2.1 TC/画面） |
| **関連** | VP-A-02（DataScope）、VP-A-04（URL攻撃）、VP-D-04（監査） |

**テスト目的**：
3層の権限チェックが一貫して機能することを保証する。

1. **FE メニューフィルタ** — `useMenu()` が permission を持たないエントリを
   非表示にし、サイドバー＋ダッシュボード上にリンクが表示されない。
2. **FE ルーターガード** — URL を直接入力 → トースト
   `アクセス権がありません。` 表示 + `/dashboard` へリダイレクト。
3. **BE API ガード** — API を直接呼び出し（DevTools／curl）→ 403 FORBIDDEN
   を返却し、`t_log` にエラーログが完全に記録される。

**テストケース設計方法**：
1. `docs/database/seeder.md §3` から権限マトリクスを作成 — 43権限 × 5ロール。
   `○` セルは正常系、`×` セルは異常系。
2. ステージング環境にロール別テストアカウントを5件作成。
3. 各画面について以下を作成：
   - 許可ロール用の正常系 TC（画面表示＋データ取得可）
   - 非許可ロール（任意の1ロール）用の異常系 TC（URL直接）
   - DevTools 経由 API 直接呼び出しの異常系 TC — 「FEで非表示なのに BE で
     許可してしまう」バグを検出

**典型的な落とし穴**：
- FE フィルタのテストだけで充足したと考えがち。実際の攻撃は API 直接呼び出し
  であるため、必ず API 層まで掘る。
- エッジケースの漏れ：`view` 権限はあるが `update` がないロール → 「編集」
  ボタン非表示 + URL `/edit` も遮断されることを検証する必要あり。
- `アクセス権がありません` （ルーターガード文言）と `権限がありません` （以前
  顧客が paraphrase したエラー文言）の混同 — 仕様は **literal copy** を要求。

**カバレッジ確認**：
- controller 内の `@Permissions('xxx.action')` （`grep -r '@Permissions'
  apps/backend/src/`）すべてに、対応する異常系 TC が1件以上存在すること。
- `AppSidebar.spec.ts` は FE フィルタ層をカバー済み（既存12テスト）。

#### VP-A-02 — データ範囲（DataScope）

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | 一覧＋詳細画面（約20画面） |
| **TC見積** | 約200（4スコープロール × 20画面 × 2.5 TC/画面） |
| **関連** | VP-A-01、VP-A-03、VP-A-04 |

**テスト目的**：
各ロールが自スコープのデータのみ閲覧できることを **list クエリと ID直接アクセス
の両面** で保証する。

| ロール | 購読者 | 販売店 | 単価／支店 | JA | レポート | ログ |
|---|---|---|---|---|---|---|
| NICHINO_ADMIN | — | — | — | 全JA | — | 全JA |
| NICHINO_STAFF | — | 全JA（代行） | — | — | — | 全JA |
| CHUOKAI | 自中央会 | 自中央会 | 自中央会 | 自JA（一部項目） | 自中央会 | 自中央会 |
| JA_HONTEN | 自JA | 自JA | 自JA | 自JA（一部項目） | 自JA配下支店 | 自JA配下支店 |
| JA_KANRI_SHITEN | 自支店 | 自JA | 自JA | — | 自支店 | 自支店 |

**テストケース設計方法**：
1. テストデータシード：最低 2中央会、各中央会2JA、各JA2支店。
2. 各ロールについて、list クエリ → スコープ内データのみ表示されることを検証。
3. スコープ外レコードの ID で直接 GET → 404 を期待（403 ではなく、レコード
   存在を秘匿するため — `data-scope.ts` ヘルパー参照）。
4. スコープ外への PATCH／DELETE → 同じく 404。

**典型的な落とし穴**：
- list クエリ（SQLフィルタ）のみテストしがち。詳細／更新／削除を URL 直接で
  検証する必要あり。
- 403 と 404 の混同 — プロジェクト規約では **スコープ外は 404** で秘匿する。
  BE が 403 を返したらバグ（`assertJaScope`／`assertBranchScope` 参照）。
- 「JA_HONTEN が JAマスタの一部項目を読み取り専用で閲覧」観点漏れ — 画面非表示
  ではなく、特定項目のみ read-only 化（VP-A-03 参照）。

**カバレッジ確認**：
- `applyJaScope`／`applyBranchScope`／`assertJaScope`／`assertBranchScope`
  を呼び出す各サービスメソッドに、対応する異常系 TC が1件以上存在すること。

#### VP-A-03 — 項目レベル制限（Field-level restriction）

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | 項目レベル制限を持つ5マスタ（`ja`、`shiten`、`kanri_shiten`、`account`、`dokusya`） |
| **TC見積** | 約50（5マスタ × 5ロール × 平均2 TC/画面） |
| **関連** | VP-A-02 |

**テスト目的**：
同じ編集画面・同じレコードでも、ロールにより編集可能な項目が異なる。編集
不可項目は read-only（input disabled）であり、その項目を含む PATCH は BE が
拒否する。

**テストケース設計方法**：
1. `.claude/rules/security.md §Layer 3` の `FIELD_RESTRICTIONS` 表を参照。
2. 各 `項目 × ロール` セル：
   - 正常系：ロール X で編集画面を開き、項目 Y が編集可能であり、新しい値で
     保存に成功する。
   - 異常系：当該ロールに権限がない項目 Y を含む PATCH を API 直接呼び出し →
     `filterAllowedFields` により Y は破棄され、BE は許可項目のみ更新する。

**典型的な落とし穴**：
- UI で disabled になっていれば pass、と判断してしまう。攻撃者は UI を
  バイパス可能であるため、必ず PATCH API 直接（DevTools）でテスト。
- 組み合わせ漏れ：項目 A の編集権あり、PATCH に A + B（B は権限なし）を
  送信 → A は更新成功、B は無視（エラーにならない）。

#### VP-A-04 — URL直接アクセス攻撃

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | パスパラメータを持つ全URL（`/ja/:id/edit`、`/dokusya/:id` など） |
| **TC見積** | 約75（約25URL × 平均3ケース） |
| **関連** | VP-A-01、VP-A-02 |

**テスト目的**：
ユーザーがスコープ外／権限外の ID で URL 直接アクセスしても FE ガードを
バイパスできない。以下を含む：

- 存在しない ID → 404（NotFound）
- 存在するがスコープ外 ID → 404（秘匿）
- スコープ内・権限不足 ID → トースト表示 + リダイレクト

**テストケース設計方法**：
1. `apps/frontend/src/router/index.ts` から URL パターン一覧を作成。
2. 各 URL について以下3ケースをテスト：
   - ID = 99999（存在しない）
   - 別 JA レコードの ID
   - 自 JA レコードだが当該ロールに `update` 権限なし

**典型的な落とし穴**：
- UI ナビゲーションのテストだけで終わってしまう。アドレスバーで URL を
  手入力／ID 改ざんするテストが必須。
- 古いブックマークから開いた場合のみ顕在化するバグもある — F5 リロードでも
  検証する。

#### VP-A-05 — セッション失効／401 ハンドリング

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | 全システム |
| **TC見積** | 約30 |
| **関連** | VP-D-02（セッションスライディング） |

**テスト目的**：
Redis セッションが失効（24h 経過または強制 revoke）した場合、次の API 呼び出し
で BE が 401 を返却する。FE は以下を実施する：

1. `useAuthStore().user` をクリア
2. `/login?redirect=current_url` へ遷移
3. ログイン画面では `セッションが切れました…` トーストを**表示しない**
   （ログインフォームが既に状態を表現している）

**テストケース設計方法**：
1. ログイン後、1タブを開いて 24h 以上待機（または admin ツールで session を
   強制 revoke）。
2. 任意のボタンをクリック → `/login` へリダイレクト + URL に `?redirect=...`
   が付くこと。
3. 再ログイン → 元の URL へ戻ること。
4. フォーム入力中の場合：フォームデータは保持されるか？（現行仕様：保持しない、
   UX ガイドに明記）

**典型的な落とし穴**：
- テスト環境でセッション TTL を短く（60秒など）設定したまま、ステージングで
  24h に戻し忘れる。
- 認証画面（login／mfa）では interceptor がリダイレクトしない仕様 — エラー
  をインライン表示する。両パスをテストする必要あり。

#### VP-A-06 — XSS／HTML 描画安全性

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | DB に保存・再表示する全テキスト入力（約20フォーム）、URL クエリ／パスから描画する全画面 |
| **TC見積** | 約50（約20フォーム × 平均2.5ベクトル） |
| **関連** | VP-A-10（SQLインジェクション）、VP-B-04 |

**テスト目的**：
FE 描画レイヤにおいて、ユーザー入力由来の HTML／JS が実行されない
ことを保証する。

1. **表示安全** — Vue の `{{ }}` 補間（自動エスケープ）を全描画箇所で使用し、
   ユーザーデータに対する `v-html` は原則禁止。例外利用時は DOMPurify
   sanitize を必須とする（プロジェクト規約 vue.md §Security）。
2. **永続 XSS** — 保存後に一覧／詳細画面を再表示してもペイロードが実行
   されない。
3. **反射 XSS／DOM XSS** — クエリ文字列・パスパラメータ・hash fragment 内の
   payload がエスケープなしで描画されない。
4. **属性インジェクション** — `<a :href="...">`、`<img :src="...">` 等の
   動的属性に `javascript:`、`data:text/html;base64,...` URL が注入されない。

テスト対象ベクトル：
- HTML タグ：`<script>alert(1)</script>`、`<img src=x onerror=alert(1)>`、
  `<svg onload=alert(1)>`
- 属性ペイロード：`<a href="javascript:alert(1)">click</a>`、
  `<iframe src="data:text/html;base64,...">`
- エンコード変種：`&#60;script&#62;`、`%3Cscript%3E`、Unicode escape
- Stored XSS：項目に payload を入力 → 保存 → 一覧／詳細画面再表示でも実行
  されない
- DOM XSS：クエリ文字列内の payload → エスケープなしで描画されないこと

**テストケース設計方法**：
1. テキスト入力項目（description、biko、name 等）の一覧を作成 — 厳密な
   format を持たない全項目。
2. 各項目 × 上記4ベクトル のマトリクスを作成。
3. 入力＋保存後、一覧／詳細画面を再表示 → payload が plain text として表示
   される（実行されない）ことを確認。
4. コードベースから `v-html` を grep し、各箇所に DOMPurify または明確な
   justification があるか確認。

**典型的な落とし穴**：
- Vue 自動エスケープで XSS の95% はカバーされるが、`v-html` でバイパス可能。
- お知らせ本文／メールテンプレート等のリッチテキストフィールドが盲点。
- 顧客テストチームは単純な payload 1-2件しかテストしないことが多い。
  エンコード変種も必ずテスト。

#### VP-A-07 — CSRF／Cookie セキュリティフラグ

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | 全システム |
| **TC見積** | 約10 |
| **関連** | VP-A-05、VP-D-02 |

**テスト目的**：
セッション Cookie に標準フラグが設定されており、CSRF およびクッキー
情報漏洩を防止できる。フラグ欠落はセッション奪取に直結するため、
リスクレベル「高」とする。

- `HttpOnly`（JS 読み取り不可 — XSS でセッション奪取不可）
- `Secure`（HTTPS のみ送信、HTTP は不可）
- `SameSite=Strict`（CSRF 対策）
- `Path=/`、`Max-Age=86400`（24h スライディング TTL — VP-D-02 と整合）

テスト：
1. DevTools → Application → Cookies → セッション Cookie のフラグを確認。
2. オリジン攻撃：別ドメインの HTML ページからフォームを API に submit →
   `SameSite=Strict` により拒否されること。
3. JS から `document.cookie` 読み取り試行 → セッションIDが取得不可
   （`HttpOnly` の効果）。
4. HTTP 経由のリクエスト試行 → 本番では Cookie が送信されない
   （`Secure` の効果）。

**典型的な落とし穴**：
- `Secure` フラグは HTTPS 本番でのみ有効。dev（HTTP localhost）では検証
  不可 — 必ずステージング環境でテスト。
- `SameSite=Lax` への意図せぬ緩和（フレームワーク既定値変更）— 各
  リリース時に DevTools で再確認すること。

#### VP-A-08 — レート制限・Throttling

| 項目 | 値 |
|---|---|
| **リスクレベル** | 中 |
| **適用範囲** | 全公開API＋認証エンドポイント |
| **TC見積** | 約20（10レート制限ルート × 2 TC：境界内成功／境界超過 HTTP 429） |
| **関連** | VP-A-09（アカウントロック）、VP-D-09（パスワード再発行クールダウン）、VP-D-01（MFA OTP） |

**テスト目的**：
NestJS `@Throttle` デコレータ（アプリ層）と AWS WAF レート制限
（インフラ層）が二層化されており、各エンドポイントの上限超過時に
HTTP 429 ＋ トースト `リクエスト回数が上限を超えました。しばらくしてから再度お試しください。`
が返却される。

主要なレート制限ルール（プロジェクト規約 security.md より）：

| エンドポイント | 制限 | 超過時応答 |
|---|---|---|
| 全公開API（既定） | 100req/分／IP | 429 TOO_MANY_REQUESTS |
| `/auth/login` | 5req/分／IP | 429 |
| `/auth/forgot-password` | 同一メール 5分クールダウン | 429 PASSWORD_RESET_RATE_LIMIT |
| OTP 再送（`/auth/mfa/resend`） | 60秒クールダウン、1ログインセッション最大3回 | 429 |
| MFA verify（`/auth/mfa/verify`） | 1OTPあたり最大5回試行 | 401 OTP_LOCKED |

**テストケース設計方法**：
各レート制限ルートで以下2 TC をペアで作成：
1. 境界内（上限直前）：N-1 回連続リクエスト → 全て成功
2. 境界超過（上限の次のリクエスト）：N+1 回目 → HTTP 429 + 想定文言

**典型的な落とし穴**：
- TC-003-073 のように VP-A-07（CSRF／Cookie）に誤割り当てされやすい —
  Throttling は独立観点。SCR-003-testcase.md 内の TC-003-073 補足にも
  「最近接観点として採用」と記録があるが、本リビジョン（v1.1）以降は
  VP-A-08 を一次マッピング先とする。
- AWS WAF のレート制限はリージョン全体集計のため、テスト環境で再現困難。
  アプリ層 `@Throttle` のみでテストし、WAF はステージング環境で別途検証。

#### VP-A-09 — アカウントロック・解除運用

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | SCR-001（ログイン）、SCR-002（MFA verify）、管理機能（アカウント解除） |
| **TC見積** | 約8 |
| **関連** | VP-A-08、VP-D-01、VP-D-04（監査ログ） |

**テスト目的**：
5回連続ログイン失敗で `t_account.account_lock_at` がセットされ、
以降のログイン試行はパスワード正否に関わらず拒否されることを保証する。
解除は admin による手動操作のみ（パスワードリセットでは解除されない）。

**テストケース設計方法**：
1. 4回失敗（境界内）→ ログインフォームに失敗トースト表示、ロックなし
2. 5回目失敗（ロック発動）→ `t_account.account_lock_at` に時刻 INSERT、
   `t_login_log` に失敗ログ記録
3. 6回目試行（正パスワード使用でも）→ HTTP 401 +
   トースト `アカウントがロックされています。管理者へお問い合わせください。`
4. パスワードリセット完了後にログイン試行 → 依然としてロック状態
   （パスワードリセットは解除しない）
5. admin による手動解除 → `account_lock_at = NULL` 更新後、ログイン成功
6. 監査ログ：ロック発動・解除それぞれが `t_log` に記録される

**典型的な落とし穴**：
- 旧 VP-D-01 が「1IP×10回」と「1アカウント×5回」を混同していた
  （ブルートフォース対策とアカウントロックは別観点）。
  本観点では「1アカウント×5回」のロックロジック専用とし、IP 単位の
  Throttling は VP-A-08 で取り扱う。
- カウンタリセット仕様の確認漏れ：成功ログイン時／一定時間経過時に
  失敗カウンタはリセットされるか — プロジェクト仕様
  （security.md `feat(auth): auto-lock account after 5 consecutive failed logins`）
  では成功時のみリセット。

#### VP-A-10 — SQL インジェクション

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | DB へクエリを発行する全フォーム＋検索画面（約20画面） |
| **TC見積** | 約30（約20入力 × 平均1.5ベクトル） |
| **関連** | VP-A-06（XSS は別観点）、VP-B-04 |

**テスト目的**：
BE クエリレイヤにおいて、ユーザー入力由来のメタ文字が SQL 構文として
解釈されない。本観点は v1.0 まで VP-A-06 と統合されていたが、JSTQB
カテゴリでは「描画安全性」と「クエリ安全性」は別カテゴリのため、
本リビジョン（v1.1）で独立化。

1. **パラメータ化強制** — TypeORM の `createQueryBuilder` または
   `find/findOne` を必須化し、`repo.query(\`SELECT … '${input}'\`)` 形式の
   生 SQL は完全禁止（プロジェクト規約 nestjs.md §Query Best Practices）。
2. **特殊文字エスケープ** — シングルクォート、セミコロン、コメント記号
   `--`、`/* */`、Unicode コードポイント等の入力時にエラーや誤動作なし、
   かつ DB に literal として保存される。
3. **ILIKE 検索安全性** — 検索画面の `WHERE col ILIKE :pattern` で
   `%`／`_` ワイルドカードがユーザー入力に含まれていても期待通りに
   動作（または明示的にエスケープ）。

テスト対象ベクトル：
- 古典的：`'; DROP TABLE m_ja; --`、`' OR '1'='1`
- UNION 攻撃：`' UNION SELECT account_id, password_hash FROM t_account --`
- ブラインド：`' AND SLEEP(5) --`、`' AND 1=(SELECT COUNT(*) FROM ...) --`
- ワイルドカード混在：`%`、`_`、`\%`、`\_`

**テストケース設計方法**：
1. 全テキスト入力＋検索条件入力に対して上記ベクトルを投入 → エラー
   レスポンス（500）が発生せず、かつデータ漏洩・破壊が起きないこと。
2. ペイロードを literal として DB に保存・再取得し、形が崩れないこと。
3. `git grep -E 'repo\.query\(|\.query\(`backtick`' apps/backend/src/`
   で生 SQL の存在チェック → 0件であること。

**典型的な落とし穴**：
- TypeORM `query()` メソッド使用時、`?` プレースホルダなしで文字列連結
  → 構造的に脆弱。レビューで必ず指摘。
- 検索画面の ILIKE 句で `%` をユーザー入力に含めると意図せぬ広範囲
  マッチが発生。意図設計か確認。
- DB ユーザの権限が広すぎる場合、SQLi 成功時の被害が大きい。
  IAM 最小権限の組み合わせで防御深度を増す（インフラ層責任）。

#### VP-B-01 — 必須項目チェック

**テストケース設計方法**：

#### VP-B-02 — 最小／最大長境界

| 項目 | 値 |
|---|---|
| **リスクレベル** | 中 |
| **適用範囲** | 約25フォーム（maxLength 設定あり） |
| **TC見積** | 約80 |
| **テスト技法** | JSTQB FL §4.3.2「境界値分析（boundary value analysis）」を適用。各項目で `min-1 / min / min+1 / max-1 / max / max+1` の6点を網羅。 |

**テスト目的**：
`maxLength=N` の各項目について：
- N 文字入力 → OK
- N+1 文字目で入力ブロック（input attribute maxLength）
- N より長い文字列を貼り付け → N 文字に切り詰め
- minLength を持つ項目：min 未満入力 → 形式エラーメッセージ

**典型的な落とし穴**：
- 半角 vs 全角：全角文字は regex により1文字または2文字としてカウント
  される可能性。BE バリデーションは一貫性を持つこと。
- 顧客は通常「1文字 / 最大文字 / 最大+1文字」のみテスト。貼り付けケースを
  忘れがち → 当該箇所でバグ多発。

| **適用範囲** | 全テキスト入力フォーム＋検索画面（約25画面） |

| **関連** | VP-B-04（半角／全角）、VP-E-03（キーボード操作） |

**テスト目的**：
日本語業務システム特有の入力経路（IME、全角貼付、a-select の
clearable など）でフォームが破綻しないことを保証する。プロジェクト
規約 vue.md で明文化されたエッジケースを観点として明示化する。

1. **IME composition 中 Enter 抑止** — `composition` イベント中に Enter 押下
   で誤送信されないこと。`preventEnterImplicitSubmit` ハンドラが導入されて
   いる4項目以上の CRUD フォームでは、IME 確定 Enter で submit されないこと。
2. **検索入力の paste 前後トリム** — `onSearch` 内で
   `state.filters.x = state.filters.x.trim()` を実行することにより、
   貼付時の前後空白・IME 確定空白が ILIKE パターンを破壊しないこと。
3. **HTML5 `type` 禁止の確認** — `type="email"` / `type="number"` /
   `type="date"` 等を使用していないこと。ブラウザ英語ポップアップが
   日本語 `<a-form-item :help>` メッセージを覆い隠す事故を防止。
4. **a-select clearable は undefined を返す** — `<a-select allow-clear>`
   の × クリック時に v-model が `undefined` 化するため、必須チェック側は
   `?.trim()` を使用していること（`.trim()` 直呼び出しで TypeError 発生
   → 全画面共通エラートースト出る既知バグ）。
5. **数値 m_code → String 強制** — radio v-model に数値値を直接バインド
   すると antd の strict-equal 比較で何も選択されない。フォームロード時に
   `String(resp.zei_kubun ?? '')` で強制すること。
6. **全角→半角自動変換** — 数値項目に `１２３` を入力 → submit 時に
   `123` へ変換（または明示的な拒否メッセージ）。

**テストケース設計方法**：
1テキスト入力につき以下3 TC をペアで作成：
- IME composition 中 Enter → submit ブロック
- 半角／全角空白を前後に貼付 → submit 時 trim 後の値が DB に保存
- 全角数字を数値項目に入力 → 変換または拒否メッセージ表示

**典型的な落とし穴**：
- 開発時はキーボード直接入力でしかテストせず、IME confirm で発生する
  バグが UAT で発覚する。日本人テスターが IME 経由で必ず再現すること。
- `placeholder="メールアドレスを入力してください"` のように
  placeholder 末尾の句点なしと、エラーメッセージ末尾の句点ありの
  差異を顧客レビューで指摘されがち（プロジェクト規約 vue.md
  §Japanese system-message punctuation 参照）。

#### VP-D-09 — パスワード再発行 旧token無効化＋クールダウン

| 項目 | 値 |
|---|---|
| **リスクレベル** | 高 |
| **適用範囲** | SCR-007（パスワード再発行） |
| **TC見積** | 約6 |
| **関連** | VP-D-03（パスワード再発行フロー）、VP-A-08（Throttling） |

**テスト目的**：
パスワード再発行フローにおいて、旧 token の使い回し攻撃と短時間の
リクエスト連投を防止する。プロジェクト規約 security.md
`feat(auth): rate-limit forgot-password + invalidate prior reset tokens`
の動作仕様を観点化する。

1. **5分クールダウン** — 同一メールアドレスからの再要求が前回から5分
   未満の場合、HTTP 429 +
   `再送信は5分後に可能です。時間をおいてから再度お試しください。`

2. **旧 token 無効化** — 新しい再発行リンク発行と同時に、同一アカウントの
   既発行・未使用 token を `t_mfa_otp.used_flg = true` に更新する
   （新 INSERT と同一トランザクション内）。
3. **列挙対策のトレードオフ確認** — 既存アカウントのみ 429 を返却し、
   非存在メールは常に 200 を返す（タイミング差で「アカウント存在」が
   推定可能だが、UX 優先で受容するトレードオフ）。
4. **旧リンククリック時の使用済み判定** — 新 token 発行後に旧メールの
   リンクをクリック → `INVALID_TOKEN` または `TOKEN_USED` で拒否。

**テストケース設計方法**：
1. 同一メール・5分以内連続申請 → 2回目が HTTP 429 + 想定文言
2. 同一メール・5分超過後の申請 → HTTP 200 + 新メール送信
3. 異メール並行申請 → 互いに干渉せず、どちらも HTTP 200
4. 既存アカウントの旧リンク（A）→ 新リンク発行（B）→ A をクリック →
   `t_mfa_otp.used_flg=true` のため拒否
5. 非存在メール連続申請 → 常に HTTP 200（429 にしない）
6. 監査ログ：再発行成功・失敗が `t_log` に記録される

**典型的な落とし穴**：
- 旧 token 無効化を新 INSERT と同一トランザクション外で実行するバグが
  入りやすい — `dataSource.transaction(...)` 内で UPDATE → INSERT を
  順に実行することを実装で確認。
- 5分計測の起点を「INSERT 直後」ではなく「クールダウン応答返却時」に
  したり、「旧 token 無効化時刻」にしたりするバグ — 起点は必ず
  `t_mfa_otp.created_at` で固定。

#### VP-E-07 — 未保存変更ガード・ブラウザ離脱

| 項目 | 値 |
|---|---|
| **リスクレベル** | 中 |
| **適用範囲** | 全 CRUD 編集フォーム（約25フォーム） |
| **TC見積** | 約8 |
| **関連** | VP-E-05（マルチタブ） |

**テスト目的**：
編集中の未保存変更があるフォームから離脱する際に、ユーザーが意図せず
入力を失わないように警告を表示する。

1. **ブラウザ離脱警告（`beforeunload`）** — 入力後にタブを閉じる／URL
   を変更する／F5 リロード → ブラウザ既定の確認ダイアログを表示する。
2. **router.beforeEach での確認モーダル** — 入力後に SPA 内画面遷移
   （メニュークリック、戻るボタン、別画面リンク）→
   `変更が保存されていません。画面を移動しますか？` モーダル表示、
   キャンセルで遷移をブロック。
3. **未変更時はガードしない** — フォームに変更がない場合は警告なしで
   遷移可能（false-positive で UX を妨げない）。
4. **保存成功後のガード解除** — submit 成功で内部 dirty フラグが
   リセットされ、続く遷移は警告なし。

**テストケース設計方法**：
1. 編集画面で1項目変更 → タブを閉じる → ブラウザ既定警告が出ること
2. 編集画面で1項目変更 → サイドバーから別画面に遷移 → 確認モーダル表示
3. 確認モーダルで「キャンセル」→ 元画面に留まること、入力値も保持
4. 確認モーダルで「OK」→ 遷移成功、入力値破棄
5. 編集画面を開いただけ／同じ値を入力（実質変更なし）→ 警告なし
6. submit 成功後に画面遷移 → 警告なし

**典型的な落とし穴**：
- TC-003-076 が VP-E-04（ブラウザ互換性）に誤割り当てされていた事例
  あり。本観点が本来の所属。SCR-003-testcase.md 内の TC-003-076
  以降は VP-E-07 へ一次マッピングし直すこと。
- `beforeunload` は SPA 内ナビゲーションでは発火しないため、
  Vue Router ガードと2系統の実装が必要。両方をテストすること。
